Do briefing ao código revisado, uma fatia por vez.

O SDD toolkit transforma o Copilot num fluxo com etapas fixas: cada etapa tem o seu agente, o seu modelo e o seu limite. Você planeja antes de codar, revisa e commita cada fatia, e só arquiva o que passou nos dois eixos de revisão.

Antes de começar

Quatro coisas na máquina. Todos os comandos desta página rodam no Git Bash, não no PowerShell nem no CMD.

VS Code com Copilot

No chat, use o harness Copilot. É nele que os agentes sdd-plan, sdd-implement, sdd-review e sdd-archive aparecem no seletor de agentes.

Git Bash, Git e Node 18 ou mais

O Git Bash vem com o Git for Windows. O instalador e os scripts do toolkit são Node puro: sem npm, sem rede.

Confira no Git Bash
node --version   # precisa ser v18 ou mais
git --version
code --version

Instalação

Um instalador para todos os cenários. Ele mostra o plano antes de escrever, nunca toca nas suas mudanças, specs, decisões e briefings, e para sem escrever nada se encontrar arquivo do toolkit alterado à mão.

caminho para usar nos comandos
"/c/Users/seu-usuario/Documents/Projetos/minha pasta/sdd-toolkit-v0.4"

Para copiar o caminho: no VS Code, botão direito na pasta e Copy Path; no Explorador do Windows, Shift + botão direito e Copiar como caminho. O caminho vai sempre entre aspas, por causa de espaços e acentos.

Global, sem .github

Use só quando o repositório proíbe commitar .github/. No modo global, cada pessoa tem a sua cópia dos agentes, e o time pode ficar em versões diferentes do contrato. Combine a versão e reinstale a cada release.

  1. Instale agentes e skills no seu usuário. Vão para ~/.copilot (ou $COPILOT_HOME), com os caminhos do contrato reescritos para essa pasta.
    terminal
    bash "<pasta-do-pacote>/instalar.sh" global --dry-run
bash "<pasta-do-pacote>/instalar.sh" global
  2. Em cada repositório, instale só .sdd/ e docs/.
    terminal
    cd "/c/Users/<seu-usuario>/Documents/Projetos/<seu-repo>"
bash "<pasta-do-pacote>/instalar.sh" repo . --sem-github --dry-run
bash "<pasta-do-pacote>/instalar.sh" repo . --sem-github
  3. Apague cópias antigas no repositório. O --sem-github não toca em .github/. Se o repositório ainda tiver .github/prompts/sdd-*.prompt.md ou .github/skills/sdd-workflow/, apague à mão: junto com a instalação global, eles aparecem duplicados. O instalador avisa quando encontra.
  4. Commite .sdd/ e docs/ e recarregue o VS Code.

BFF + front juntos

Para o plano ser fiel, o agente precisa ler os dois códigos. Abra os dois repositórios no mesmo workspace do VS Code. A regra que não muda: cada repositório tem o seu .sdd/ e a sua mudança, ligadas pelo mesmo Ticket:, e o contrato (OpenAPI) é tratado isoladamente em cada camada. O front nunca importa arquivo do repositório do BFF; ele lê o contrato como referência e mantém a própria cópia gerada.

  1. Instale o toolkit nos dois repositórios, com a aba "Repositório novo" ou "Global" em cada um.
  2. Crie um workspace com as duas pastas. Salve o arquivo fora dos dois repositórios e coloque primeiro o repositório onde você vai rodar o agente.

    Ou pelo menu: File → Add Folder to Workspace… e depois File → Save Workspace As…. Abra com File → Open Workspace from File….

3

Configurar o verificacao.json

Este arquivo diz ao toolkit o que é camada no seu projeto e qual comando roda em cada uma. Com ele, a revisão verifica só a camada que a mudança tocou: erro que já existia é contado e não bloqueia; erro que a mudança criou, bloqueia.

O que cada campo faz

camadas.<nome>.arquivos
globs da camada, como src/app/feature/**. O primeiro que casar vence.
camadas.<nome>.verificacoes
nomes das verificações que valem para ela.
comando
com {arquivos} roda só nos arquivos tocados; sem ele roda uma vez.
formato
eslint-json, jest-json ou linhas (este exige padrao com os grupos arquivo, linha e mensagem).
classificacao
base-stdin (lint, exato), baseline (tipos e testes, exato com linha de base) ou linhas-alteradas (aproximado).
Molde que vem no pacote .sdd/verificacao.json
verificacao.json
{
  "verificacoes": {
    "lint": {
      "comando": "npx eslint -f json {arquivos}",
      "comandoBase": "npx eslint -f json --stdin --stdin-filename {arquivo}",
      "extensoes": [".ts", ".html"],
      "formato": "eslint-json",
      "classificacao": "base-stdin"
    },
    "tipos": {
      "comando": "npx tsc --noEmit --pretty false -p tsconfig.app.json",
      "formato": "linhas",
      "padrao": "^(?<arquivo>[^\\s(][^(]*)\\((?<linha>\\d+),\\d+\\): error (?<mensagem>.+)$",
      "regra": "tsc",
      "classificacao": "baseline"
    },
    "testes": {
      "comando": "npx jest --ci --passWithNoTests --json --outputFile={saida} --findRelatedTests {arquivos}",
      "comandoBaseline": "npx jest --ci --passWithNoTests --json --outputFile={saida} {raizes}",
      "extensoes": [".ts"],
      "formato": "jest-json",
      "classificacao": "baseline"
    }
  },
  "camadas": {
    "core": { "arquivos": ["src/app/core/**"], "verificacoes": ["lint", "tipos", "testes"] },
    "domain": { "arquivos": ["src/app/domain/**"], "verificacoes": ["lint", "tipos", "testes"] },
    "feature": { "arquivos": ["src/app/feature/**"], "verificacoes": ["lint", "tipos", "testes"] },
    "shared": { "arquivos": ["src/app/shared/**"], "verificacoes": ["lint", "tipos", "testes"] }
  }
}

Peça para o Copilot adaptar ao seu projeto

Chat novo, agente padrão Agent, na raiz do repositório. Cole o prompt inteiro.

prompt para o Copilot
Reescreva somente o arquivo .sdd/verificacao.json deste repositório. Não altere nenhum outro arquivo.

1. Leia angular.json (ou project.json), os tsconfig*.json, a configuração do ESLint (eslint.config.* ou .eslintrc*), a do Jest (jest.config.* ou a seção jest do package.json) e a estrutura de pastas de src/app/.

2. Mantenha exatamente o schema atual do arquivo:
   - "verificacoes": cada entrada tem "comando", "formato" (eslint-json, jest-json ou linhas) e "classificacao" (base-stdin, baseline ou linhas-alteradas).
     O lint usa "comandoBase" com {arquivo} e --stdin --stdin-filename.
     O formato linhas exige "padrao", uma regex com os grupos nomeados arquivo, linha e mensagem.
     Testes com classificacao baseline usam "comandoBaseline" com {raizes} e --outputFile={saida}.
   - "camadas": cada camada tem "arquivos" (lista de globs) e "verificacoes" (lista de nomes).

3. Crie uma camada para cada pasta real da arquitetura (por exemplo core, domain, feature, shared). Não crie camada para pasta que não existe.

4. Use as ferramentas que o projeto já tem, via npx, e o tsconfig real da aplicação. Se uma ferramenta não existir, remova a verificação dela e diga por quê. Não instale nada.

5. Confirme que funciona:
   - rode node -e "JSON.parse(require('fs').readFileSync('.sdd/verificacao.json','utf8'))"
   - rode cada "comando" trocando {arquivos} por um arquivo real de cada camada e mostre que ele executa.

6. Termine com uma tabela: camada, globs, verificações. Depois liste o que precisa da minha confirmação.

Revise o diff e commite. A partir daí, o sdd-plan lê este arquivo para declarar o Escopo: de cada mudança, e o validador recusa camada que não existe nele.

Briefing

você escreve

Uma página em português comum: o problema, o que se espera, o que não pode ser feito e o que está fora do escopo. Pergunta sem resposta fica marcada como [NÃO RESPONDIDO]. Não escreva critério de aceite: isso é trabalho do plano.

Exemplo docs/briefings/confirmacao-duplicada/briefing.md
briefing.md
# Briefing - Pix confirmado duas vezes em rede lenta

## Problema

Em conexão lenta, o cliente toca em "Confirmar" mais de uma vez na tela de confirmação de Pix
e o BFF recebe duas transferências iguais. A Ouvidoria registrou reclamações de débito em dobro.

## O que se espera

Um toque a mais em "Confirmar" não pode gerar uma segunda transferência.

## Restrições

- O layout da tela de confirmação não muda: foi aprovado por UX e Compliance.
- O contrato do endpoint POST /pix/transferencias no BFF não muda nesta entrega.
- Nenhum dado de conta ou chave Pix vai para log.

## Fora do escopo

- Pix agendado e Pix Saque.
- Reenvio automático em caso de timeout.

## Contexto útil

O BFF já aceita o header Idempotency-Key no POST /pix/transferencias (ver docs/openapi.yaml do BFF).

## Prazo e ticket

PIX-482. Por quanto tempo a chave de idempotência vale no BFF? [NÃO RESPONDIDO]

sdd-plan

Claude Opus 5read, search, edit, execute

Transforma o briefing num acordo escrito antes de qualquer linha de código: proposta, tarefas em fatias verticais e, quando preciso, design e deltas de especificação. Lê o Git para descobrir branch e base, e nunca escreve nele.

Use quando

  • há um briefing novo para planejar;
  • a revisão reprovou e é preciso um agrupamento que corrija o achado;
  • a implementação encontrou uma decisão durável que o plano não previu.

Não use para

  • escrever código ou corrigir bug sem briefing;
  • criar ou trocar de branch;
  • refazer o plano de uma mudança sem dizer qual: ele pede o change-id.
mensagem no chat, agente sdd-plan
docs/briefings/confirmacao-duplicada/briefing.md
replanejar depois de um REPROVADO
docs/briefings/confirmacao-duplicada/briefing.md replanejar: evitar-confirmacao-duplicada

No exemplo do Pix, ele copia as restrições do briefing sem parafrasear, lê o índice de specs e só a capacidade pagamentos-pix, classifica como Full (a decisão sobre a chave de idempotência é durável) e declara o escopo de verificação domain, core, feature. Se a ambiguidade impedir um critério verificável, ele para e lista as perguntas em vez de supor.

sdd-implement

Claude Sonnet 5read, search, edit, execute

Uma fatia por sessão. Ele executa um agrupamento de tarefas, por exemplo 1.1 e 1.2, e para. Não começa o agrupamento 2 nem que você peça "continua" no mesmo chat: a fatia passa pela sua revisão e pelo seu commit antes. Na sessão seguinte, se houver alteração não commitada fora da pasta da mudança, ele recusa começar.

O que ele faz

  • confere que você está na branch declarada na proposta;
  • grava a linha de base de erros antes da primeira edição;
  • faz a menor mudança por tarefa e roda o verificador;
  • marca [x] só sem achado BLOQUEANTE.

O que ele não faz

  • trocar de branch ou commitar;
  • corrigir erro que já existia, mesmo no arquivo que editou;
  • editar proposta, design, deltas, specs ou decisões;
  • seguir para a próxima fatia.

Revisar e commitar a fatia

você

Este passo é seu, e é o que mantém o controle: cada agrupamento vira um commit que você leu. O toolkit nunca escreve no Git.

sdd-review

Claude Opus 5read, search, execute, edit

Audita a mudança em dois eixos independentes e grava um veredito por eixo: APROVADO ou REPROVADO, sem meio-termo. Exige árvore limpa e compara o diff entre base e branch.

Eixo de padrões

  • roda primeiro, sem ler a proposta;
  • julga só as linhas que a mudança alterou, contra .sdd/padroes.md e as instructions do projeto;
  • sugere promover achados recorrentes a regra de lint.

Eixo de especificação

  • critério contra código e teste: código sem teste é cobertura parcial;
  • toda tarefa [x] precisa de evidência;
  • roda o validador e o verificador por escopo.

sdd-archive

Claude Sonnet 5read, search, edit, execute

Fecha a mudança: aplica os deltas em .sdd/specs/ exatamente como foram escritos, promove as decisões permanentes para .sdd/decisoes/, atualiza os índices e move a pasta para .sdd/changes/archive/.

Só arquiva quando

  • os dois eixos estão APROVADO no commit atual;
  • todas as tarefas estão [x];
  • a árvore está limpa, exceto revisao/.

Para antes de gravar se

# Evitar confirmação duplicada de Pix

Ticket: PIX-482
Branch: feature/PIX-482-confirmacao-duplicada
Base: develop

## Intenção

Clientes em rede lenta tocam em "Confirmar" mais de uma vez e geram duas transferências Pix
iguais. A mudança garante que uma intenção de pagamento gere no máximo uma transferência,
usando o header Idempotency-Key que o BFF já aceita.

## Escopo

Dentro:
- Bloqueio do botão Confirmar enquanto a transferência está em envio.
- Envio do header Idempotency-Key, estável por intenção de pagamento.

Fora:
- Pix agendado e Pix Saque.
- Reenvio automático em caso de timeout.
- Qualquer alteração no BFF.

## Restrições

- O layout da tela de confirmação não muda: foi aprovado por UX e Compliance.
- O contrato do endpoint POST /pix/transferencias no BFF não muda nesta entrega.
- Nenhum dado de conta ou chave Pix vai para log.

## Critérios de aceite

1. Um segundo toque em Confirmar MUST NOT gerar uma segunda transferência.
   - dado uma transferência em envio, quando o cliente toca de novo em Confirmar, então nenhuma nova requisição é enviada.
   - dado que o envio falhou, quando o cliente toca em Confirmar, então a transferência é enviada de novo com a mesma chave.
2. Toda confirmação de Pix MUST enviar uma chave de idempotência estável por intenção de pagamento.
   - dado uma nova intenção de pagamento, quando o cliente confirma, então a requisição leva uma chave nova.
   - dado a mesma intenção, quando o cliente confirma de novo após erro, então a chave é a mesma da primeira tentativa.

# Design - evitar confirmação duplicada de Pix

## Abordagem

A chave de idempotência nasce no front quando a tela de confirmação abre e acompanha a
intenção de pagamento até o fim. Um interceptor HTTP anexa o header só nas chamadas de
transferência. O componente bloqueia o botão enquanto há envio em andamento, sem mudar o layout.

## Decisões

### Chave de idempotência gerada no front por intenção de pagamento
Durabilidade: permanente
Capacidades: pagamentos-pix

Restrição: o contrato do BFF não muda, e ele já aceita Idempotency-Key.
Escolha: gerar a chave ao abrir a confirmação e reaproveitá-la em toda nova tentativa da mesma intenção.
Alternativas descartadas: chave por sessão no BFF, porque não distingue duas intenções legítimas seguidas; bloqueio só no botão, porque não cobre requisição repetida pela rede.
Consequência aceita: recarregar a página cria uma intenção nova e, portanto, uma chave nova.

### Bloqueio do botão pelo estado do componente
Durabilidade: local

Restrição: o layout não muda.
Escolha: desabilitar o botão existente durante o envio, usando o indicador de carregamento que a tela já tem.
Alternativas descartadas: overlay de carregamento, porque altera o layout aprovado.
Consequência aceita: o bloqueio vale só para esta tela.

- src/app/feature/pix/confirmacao-pix.component.ts (alterado)

Guardrails: o que impede o fluxo de sair dos trilhos

Regra que cabe em código está em código. O resto é contrato, e o contrato diz onde termina.

Controle

Uma fatia por sessão
O implement fecha um agrupamento e para. A próxima sessão recusa começar com alteração não commitada.
Git só leitura
Nenhuma etapa cria branch, commita ou abre PR. O implement recusa a branch errada.
Modelo fixo por etapa
Opus para planejar e revisar, Sonnet para implementar e arquivar, declarado em cada agente.
Ferramentas mínimas
Cada agente declara só o que usa, e nenhum é acionado por outro agente sem você escolher.

Qualidade

Para em vez de supor
Ambiguidade que impede um critério verificável vira pergunta, não palpite.
Dois eixos de revisão
Padrões sem ler a proposta, especificação depois. Um não compensa o outro.
Aprovação presa ao commit
O veredito leva o commit no nome. Codou depois de aprovar, revisa de novo.
Verificação por escopo
Bloqueia o que a mudança criou, camada fora do escopo e ferramenta que falhou. Dívida antiga é contada, não corrigida às escondidas.

Segurança da instalação

Plano antes de gravar
--dry-run mostra cada arquivo e a ação.
Dados do time intocáveis
Mudanças, specs, decisões e briefings nem são lidos.
Edição local protegida
Arquivo do toolkit alterado à mão vira CONFLITO, provado por hash; --forcar faz backup antes.
Sem rede, sem npm
Node puro, finais de linha LF garantidos para o Git Bash.

O que continua dependendo de disciplina. No harness Copilot, a ferramenta de edição não separa criar de editar, então "a revisão só cria o arquivo de veredito" é regra de contrato. Se a revisão editar código, o archive pega, porque exige árvore limpa. E o terminal que os agentes usam permite git commit: o que fecha isso é a allowlist de comandos da organização.

Quando algo dá errado

Os agentes não aparecem no seletor

Confira se o chat está no harness Copilot, se os arquivos estão em .github/agents/ na raiz do workspace (ou em ~/.copilot/agents na instalação global) e recarregue a janela. Com várias pastas no workspace, deixe primeiro o repositório onde você vai trabalhar.

Digitei /sdd-plan e ele pediu para trocar de agente

É o comportamento esperado. O comando só roda com o agente da etapa, que fixa modelo e ferramentas. Abra um chat novo, selecione sdd-plan e envie o mesmo pedido.

O implement recusou começar: "alteração não commitada"

A fatia anterior ainda não foi commitada, ou há trabalho de fora da mudança na árvore. Revise e commite a fatia; se for outra coisa, guarde com git stash e rode de novo.

O implement diz que a branch é diferente da declarada

Ele nunca troca de branch. Troque você e rode de novo:

terminal
git switch <branch-da-proposta>
"node: command not found" ou versão abaixo de 18

Instale o Node LTS, feche e reabra o Git Bash e o VS Code, e confira:

terminal
node --version
which node
Erro pipefail\r: invalid option ao rodar o instalador

O instalar.sh foi salvo com final de linha do Windows. Rode direto pelo Node, que não depende disso:

terminal
node "<pasta-do-pacote>/instalar.mjs" repo . --dry-run
O instalador acusou CONFLITO

Um arquivo do toolkit foi alterado à mão, e nada foi gravado. Compare com o pacote, leve o que importa para outro lugar, e aceite a versão do pacote com backup:

terminal
bash "<pasta-do-pacote>/instalar.sh" repo . --forcar
O verificador diz "camada alterada fora do Escopo declarado"

A mudança mexeu numa camada que o plano não previu. Ou o arquivo não deveria ter mudado, ou o plano precisa ser ampliado com o sdd-plan e replanejar:.

O verificador diz "FALHOU ao executar"

O comando dessa verificação no verificacao.json não roda no seu projeto. Rode-o à mão com um arquivo real, corrija e tente de novo. Ferramenta que não roda bloqueia: verificação que não aconteceu não aprova nada.

O archive recusou mesmo com os dois APROVADO

Houve commit depois da revisão, então o veredito não vale para o commit atual. Rode os dois eixos de novo.
